# 거래소 장애 자료: 공지·엔진·연결 상태의 PIT 경계

확인일: **2026-10-25 UTC**. [기존 장애 사건 POC A](alternative-signals.md)의 입력 계약 보완이다. 새 신호·구현 결함·전략 승인·동결 실험 변경이 아니다. 공식 문서의 설명과 아래 검증 제안을 구분한다. **시장자료, 현재 장애, 실제 수신 지연, 백테스트/OOS 성과는 확인하지 않았다.**

## 1. 현재 보이는 사건 목록은 당시 받은 공지 목록이 아니다

[Atlassian의 backfill 문서][SP01]는 과거 발생일을 지정한 사건을 나중에 추가할 수 있고 이때 구독자 알림은 발송하지 않는다고 설명한다. 따라서 알림만 모은 목록과 나중 조회한 역사가 다를 수 있다. 이는 플랫폼 기능의 근거이지 **Kraken/Coinbase가 특정 사건을 소급 작성·은폐했다는 증거가 아니다.**

[Kraken Status API 문서][SP02]의 전체 사건 목록은 최근 50건이다. 예제의 작성·표시·수정 시각이 불변 최초 공개시각을 보장하지 않는다. 문서의 2014년 예제 사건을 현재 장애로 해석하지 않는다.

**제안:** 알림 수집과 공개 목록 대조는 별도 커버리지다. 뒤늦게 발견한 과거 날짜의 사건은 실제 발견 이후에만 사용할 수 있다. 현재 목록만으로 오래된 빈티지나 무장애 대조기간의 완전성을 인증하지 않는다.

## 2. 엔진 모드와 advisory 목록을 분리한다

[Kraken REST SystemStatus 문서][KS02]의 현재 설명:

- 예정 advisory는 앞으로 **72시간 이내**의 창을 포함하고, 해당 점검 창이 시작되면 목록에서 빠진다.
- emergency는 미해결 Statuspage 사건을 담고 resolved 때 빠진다.
- 최상위 엔진 `status`는 두 advisory 배열과 독립적이다.

**추론:** 예정 항목의 소멸은 복구 증거가 아니다. 72시간은 이 제품의 예정 항목 선택 범위이지 역사 보존기간이나 WS 전체의 보장된 창 길이가 아니다. 예제 `timestamp`를 최초 공개·마지막 전환 시각으로 해석할 근거도 이번 검토에서 확정하지 못했다.

[WS v2 status 문서][KS01]는 접속 성공 및 엔진 모드 변경 때 자동 status를 보낸다고 설명한다. 직접 status 요청은 없다. 부가 advisory 배열은 통합 기능이 켜진 배포에만 존재하며, 두 배열은 함께 나타나거나 함께 생략된다. 기능이 켜졌지만 대상이 없으면 빈 배열이다. 제목은 Statuspage에서 온다.

**제안:** 재접속 직후 status를 새 장애 전환으로 자동 집계하지 않는다. 연결 epoch, 엔진 모드, advisory의 미제공/빈 목록/관측 항목을 분리한다. 다른 전송 경로로 받은 같은 원천을 독립 corroboration으로 세지 않는다. advisory ID와 Statuspage ID가 동일한 namespace라고 가정하지 않는다.

## 3. heartbeat는 연결 관측이지 거래소 전체 건강 판정이 아니다

[WS v2 heartbeat 문서][KS03]는 채널 구독 후 다른 채널 갱신이 없을 때 약 1초마다 heartbeat가 생기며, 별도 payload 값은 없다고 설명한다.

**제안:** 다른 업데이트가 도착하는 동안 독립 heartbeat가 없다는 이유로 장애를 만들지 않는다. 실제 캡처 공백도 로컬 네트워크·클라이언트 실패와 거래소 문제를 구분하기 전에는 unknown이다. Kraken spot 상태를 Binance USD-M 장애나 BTC 가격 방향으로 치환하지 않는다.

## 4. 최소 acceptance 계약 — 제안이며 실행하지 않음

기존 `EventTs` / `AvailableTs` / `ReceivedTs` 의미를 바꾸지 않는다. 담당 개발자가 기존 구조에 맞춰 채택 여부를 정한다. 새 범용 검사 계층을 요구하는 문서가 아니다.

| 합성 입력 상황 | 기대 관측/재생 경계 |
|---|---|
| 과거 날짜의 사건이 오늘 처음 목록에 등장하고 알림은 없음 | 실제 발견·수정 수신시각 보존; 어제의 재생에는 보이지 않음 |
| 예정 항목이 시작시각 전에는 있고 시작 후 사라짐 | 과거 관측을 삭제하지 않음; 소멸만으로 정상 복구 판정하지 않음 |
| 재접속 후 기존 엔진 모드를 다시 수신 | 새 연결 관측과 실제 상태 전환을 구분 |
| advisory 필드 생략, 빈 배열, 항목 존재 | 세 관측을 구분; 캡처 실패도 별도 unknown |
| 비-heartbeat 채널 메시지가 계속 도착 | heartbeat 단독 미수신으로 장애 판정하지 않음 |
| 두 경로가 동일 사건을 가리키거나 서로 충돌 | 근거 있는 사건 계보로 중복 제거; 불일치는 숨기지 않고 남김 |

최소 보존 제안은 출처/제품/경로, 연결·캡처 epoch, 실제 수신시각, 출처가 주장한 발생·예정 시각, 사건/update 식별자, payload revision, 관측 가능 범위다. 발생·예정·최초 공개·최초 수신을 서로 대체하지 않는다. 출처의 현재 기능을 과거 연도에 소급 적용하지 않는다.

## 5. 연구와 접근의 기각·보류 조건

기존 BTCUSDT 사건 연구의 **주 지평 5–60분, 보조 4시간**을 유지한다. API/매칭 제한과 표시 오류, 예정 점검과 예기치 않은 사건을 나눈다. 공지 전 수익률·변동성·거래량·요일/시간대가 비슷한 정상 기간을 기준으로 쓰고 같은 사건의 여러 업데이트는 군집화한다. 급변이 장애를 먼저 유발하는 역인과, 공급자의 상태·심각도 자기보고, 사후 유명 사건 선택도 통제한다.

과거 발생시각 소급, 목록 소멸, 재접속 중복 또는 같은 원천의 다중 집계에 의존하는 효과는 기각한다. 시간순 OOS·탐색 수·실제 지연을 고정한 뒤에도 기준모형 대비 증분효과가 없으면 채택하지 않는다. 거래 주장에는 실제 가능한 다른 거래소의 체결과 수수료·스프레드·슬리피지·funding이 추가로 필요하다. 캔들만으로 체결 가능성을 증명하지 않는다.

**시간당 리서치 호출과 collector 주기는 별개다.** 이번에는 연결·폴링·구독을 실행하지 않았다. 재연결 손실, 실제 발송/수신 지연, 역사 replay, 배포별 필드 존재는 미측정이다.

[Statuspage API 구분 문서][SP03]의 인증 Manage API 제한을 공개 Status API에 전용하지 않는다. 문서는 후자를 rate limited가 아니라고 설명하지만 거래소별 SLA·중간 계층 제한 부재·무제한 수집 권리가 아니다. 공개 문서 열람은 데이터 보관/재배포 허가가 아니며 실제 이용조건·호출정책·저장비용은 수집 전에 확인한다. 신규 계정·키·결제·서명 endpoint·실거래는 하지 않았다.
